# Frozen direct-inference procedure v1

The model receives scientific task instructions and numerical test inputs, then emits actual predictions as constrained JSON. It cannot call tools, access files/network, generate an executable solution, fit a model externally or update its weights. The harness uses no model-generated code. Each task retains its native target, units and scorer; no mixed-metric universal accuracy is calculated.

The primary zero-shot condition contains no training labels. If prepared, the eight-example condition uses uniformly spaced training indices selected without examining their labels or model performance. These are in-context examples, not weight updates. Compare the conditions separately. Specialists may have undergone substantial prior task-specific training; this practical comparison does not imply equal learning budgets.

Inputs use full Python JSON floating-point representations, not rounded features or selected summary statistics. Nonfinite inputs become JSON null. IDs are local row positions, not specimen IDs or source filenames. Label meanings and the original feature names are supplied. Test targets are not loaded during prompt construction. A model receives no score feedback. Requests are sealed by SHA256, and numerical prompts remain outside Git to respect source-data redistribution restrictions.

The initial four tasks use their previously frozen custom input/split/scorer contracts as an explicitly authorized fallback. This does not convert them into official published benchmarks. Full retained test sets are queued; a partial batch is a pilot/partial result, never a completed benchmark. Official restoration and specialist-score matching remain independent admission work. Candidate sources in the 30-task map are leads, not verified winners. Exact matching requires compatible evaluation cases, inputs, targets, metric and aggregation; published scores from other settings stay contextual.

All four model IDs are checked through the API. Requests use the same scientific prompt and response schema, `store=false`, no tools and fixed batch membership. Reasoning models use medium effort with an 8192-token output ceiling; GPT-4.1 uses 2048 tokens and no reasoning parameter. Different reasoning/output budgets are disclosed. Version aliases may change; returned model IDs are recorded rather than asserting immutable snapshots for Sol aliases.

The first execution gate dispatches one K01 input batch to each of the four models. This checks generation, parsing, output IDs and usage. It is not used to tune scientific prompts based on accuracy. Infrastructure failures are retained. No automatic regeneration after a model error; resumption skips already-dispatched attempts. The bridge reserves conservative maximum request costs and enforces a $5 total ceiling, including in-flight reservations. It only accepts hashed requests listed in the frozen inventory.

After raw responses are saved, the scorer validates exact expected row IDs, finite values, class labels/probability bounds and completeness. Malformed, refused, truncated or missing outputs remain failures; they are not replaced with predictions. Full-case numerical scores are reported only when complete. Partial coverage is reported separately with its denominator and cannot be compared with a full-test published number. Grouped metrics retain source donor/mouse weighting. Uncertainty, when calculated, uses scientific groups rather than independent frame/spot assumptions.

The older code-generation study remains intact. No model score, specialist prediction, fitted model or manually repaired generated program from it is a direct-inference measurement.
